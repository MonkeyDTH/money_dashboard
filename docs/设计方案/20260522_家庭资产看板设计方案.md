# 家庭资产看板 Web 应用设计方案

**日期**：2026-05-22
**状态**：方案已确认，待开始实现

---

## 一、背景与动机

希望有一款工具，能持续跟踪家庭的财务状况，替代目前散落在 Excel / 手机记账 App 里的零散数据。
核心使用场景是**月底定期录入 + 长期趋势观察**，而不是日常每一笔记账。具体诉求：

1. **资产快照**：每月底登记一次各账户余额（活期、定期、基金、股票、公积金、房产估值等），形成时间序列。
2. **支出汇总**：按大类别（餐饮、住房、交通、教育、医疗……）记录每月支出总额，不需要逐笔记账。
3. **账户归属**：能区分"家庭共同"和"个人"账户，分别看也能汇总看。
4. **薪资明细**：按月记录个人收入的完整结构（基本工资、奖金、五险一金、个税、专项扣除等）。
5. **职业变动**：能处理跳槽，不同时间段的收入挂在不同公司下，便于横向对比与职业轨迹回顾。
6. **可视化看板**：净资产趋势、收支比、资产配置占比、年度结余等。

目标是「**5 分钟录完一个月，10 秒看完整体状况**」。

## 二、已确认的关键决策

| 编号 | 决策内容 | 选择 |
|------|---------|------|
| D1 | 部署形态 | **B. Docker 部署到自建小服务器**（amd64 镜像，浏览器 + 手机均可访问） |
| D2 | 单人 / 多人 | **单人使用**，不做鉴权（后续如需可加） |
| D3 | 薪资按人区分 | **暂时只记本人**，数据模型仍保留 `Member` 实体以便未来扩展 |
| D4 | MVP 范围 | 账户管理 + 月度余额录入 + 净资产趋势图 + 薪资明细录入 + **数据导入导出** |
| 技术栈 | 前后端 | **FastAPI + Jinja2 + HTMX + Alpine.js + Tailwind CDN**（保持轻量，SSR 为主） |
| 数据库 | 存储 | **SQLite**（单文件，挂卷持久化即可） |
| ORM | 数据访问 | **SQLModel**（FastAPI 配套，pydantic + SQLAlchemy 一体） |
| 历史数据迁移 | 范围 | 包含在 MVP，第一版即提供 Excel/CSV 导入导出 |

> **设计理念**：避免 SPA 复杂度。页面以服务端渲染为主，HTMX 处理局部交互（表单提交、表格刷新、模态框），Alpine.js 处理纯前端的轻状态（折叠、下拉、tab 切换）。Tailwind 用 CDN，零构建。

## 三、数据模型设计

### 3.1 实体关系总览

```
Member (家庭成员)
  └── SalaryRecord (月度薪资) ──── Company (公司)
        └── SalaryItem (薪资明细项)

Account (账户)
  ├── 归属: 家庭共同 / 某个成员
  └── AccountSnapshot (月度余额快照)

ExpenseCategory (支出大类)
  └── MonthlyExpense (月度支出汇总)
```

> 即便 MVP 只有一个成员（你），仍保留 `Member` 实体并预先建好关系，避免后续扩展时改表结构。

### 3.2 字段定义

#### Member（成员）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| name | string | 姓名 / 昵称 |
| is_self | bool | 是否本人（默认展示用） |

#### Account（账户）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| name | string | 账户名（如"招行储蓄卡"、"支付宝余额宝"、"华泰证券A股"） |
| type | enum | 现金 / 活期 / 定期 / 货币基金 / 股票 / 基金 / 公积金 / 房产 / 车辆 / 负债 / 其他 |
| owner_type | enum | family（家庭共同）/ member（归属某人） |
| owner_member_id | int? | owner_type=member 时关联 |
| currency | string | 默认 CNY |
| is_active | bool | 已销户的账户标记为 false，不再要求录入 |
| note | text | 备注 |

> **设计要点**：账户类型既包含资产也包含负债（信用卡欠款、房贷余额等）。计算净资产时，负债 type 的余额取负。

#### AccountSnapshot（账户月度余额）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| account_id | int | 关联账户 |
| period | date | 录入归属月份（统一存月末，如 2026-05-31） |
| balance | decimal(14,2) | 余额（统一存正数，方向由 Account.type 决定） |
| recorded_at | datetime | 实际录入时间 |

> 一个账户在一个 period 只允许一条记录（`(account_id, period)` 唯一索引）。

#### ExpenseCategory（支出大类）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| name | string | 餐饮、住房、交通、教育、医疗、娱乐、人情往来、其他 |
| color | string | 图表颜色 |
| sort_order | int | 显示顺序 |

#### MonthlyExpense（月度支出汇总）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| category_id | int | 关联大类 |
| period | date | 归属月份（月末） |
| amount | decimal(14,2) | 当月总支出 |
| owner_type | enum | family / member |
| owner_member_id | int? | 个人支出时关联 |
| note | text | 备注 |

> MVP 阶段不强制录入支出，但表结构先建好。Phase 2 启用录入界面。

#### Company（公司）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| name | string | 公司名 |
| start_date | date | 入职时间 |
| end_date | date? | 离职时间，null = 在职 |
| member_id | int | 归属成员 |
| note | text | 职位、城市等备注 |

#### SalaryRecord（月度薪资）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| member_id | int | 成员 |
| company_id | int | 公司 |
| period | date | 工资归属月份（月末） |
| pay_date | date | 实际发薪日 |
| gross | decimal(14,2) | 应发合计（冗余字段） |
| net | decimal(14,2) | 实发合计（冗余字段） |
| note | text | 备注 |

#### SalaryItem（薪资明细项）
| 字段 | 类型 | 说明 |
|------|------|------|
| id | int | 主键 |
| salary_record_id | int | 关联薪资记录 |
| item_type | enum | base（基本工资）/ bonus（奖金）/ allowance（津贴）/ overtime（加班费）/ stock（股权激励）/ social_insurance（社保个人部分）/ housing_fund（公积金个人部分）/ income_tax（个税）/ other_deduction（其他扣除）/ other_income（其他收入） |
| amount | decimal(14,2) | 金额（统一存正数） |
| direction | enum | income（收入项）/ deduction（扣除项） |
| label | string | 自定义名称（如"年终奖"、"季度绩效"） |

> **设计要点**：
> - `item_type` 是固定枚举便于横向对比和图表分类；`label` 让你给同类项起具体名字。
> - `direction` 显式存储而非由 type 推断，是为了应付"个税退税"、"社保补缴"这种例外。
> - `gross` 和 `net` 冗余存在 SalaryRecord 上，录入时自动重算，避免每次列表都聚合。

## 四、功能模块

### 4.1 看板首页（Dashboard）
- **关键指标卡片**：当前净资产、本月较上月变化、本月收入（薪资）、本月支出（Phase 2）、本月结余（Phase 2）
- **净资产趋势图**：折线图，按月，可切换"家庭总" / "仅个人"
- **资产配置环形图**：按账户类型聚合（现金 / 股票 / 基金 / 不动产 / 负债…）
- **近 12 个月收入柱状图**：MVP 先看收入，支出在 Phase 2 接入

### 4.2 月度录入向导
设计成"清单式 checklist"，进入当月录入流程：

```
2026 年 5 月录入
─────────────────
☑ 账户余额（共 8 个账户，已录 8/8）
☐ 薪资明细（招商银行 5 月，未录入）
─────────────────
[继续录入]
```

支持「**复制上月**」一键填充各账户余额，再手工调整变化项。降低录入摩擦的关键。

### 4.3 账户管理
- 账户增 / 改 / 停用
- 查看单个账户的历史余额曲线
- 余额录入表格（一屏可批量填写当月所有账户）

### 4.4 薪资管理
- 公司时间轴（可视化职业经历，含在职 / 已离职状态）
- 单条薪资明细录入页（按 `item_type` 分组填写，自动算 gross/net）
- 月度对比表（行 = 明细项，列 = 月份）
- 跨公司对比（如"招行平均月薪 vs 字节平均月薪"）—— Phase 3

### 4.5 数据导入导出（MVP 必含）
- **导出**：全库一键导出为 Excel（多 sheet：accounts / snapshots / salaries / items / companies），同时支持 SQLite 文件备份下载
- **导入**：提供 Excel 模板，校验通过后批量入库；导入幂等（按 `period + account_id` / `period + company_id` 去重）

### 4.6 支出管理（Phase 2）
- 类别管理
- 月度支出表格（行 = 类别，列 = 月份）
- 类别趋势对比图

## 五、技术选型

| 层 | 选型 | 说明 |
|----|------|------|
| 后端框架 | **FastAPI** | 异步、文档自动生成、生态丰富 |
| 模板引擎 | **Jinja2** | FastAPI 原生支持 |
| ORM | **SQLModel** | pydantic + SQLAlchemy 一体，定义模型即建表 + 校验 |
| 数据库 | **SQLite** | 单文件，挂 Docker 卷即可持久化 |
| 迁移工具 | **Alembic** | SQLModel 兼容，处理后续表结构变更 |
| 前端交互 | **HTMX** | 局部刷新表单 / 表格 / 模态框，避免 SPA 复杂度 |
| 前端状态 | **Alpine.js** | 纯前端轻状态：折叠、tab、下拉 |
| 样式 | **Tailwind CSS（CDN）** | 零构建，开发即所见即所得 |
| 图表 | **ECharts（CDN）** | 折线、环形、柱状一站式 |
| 部署 | **Docker + docker-compose** | 单服务，sqlite 文件挂卷 |
| Python 版本 | **3.11+** | match-case、性能、类型注解齐全 |
| 依赖管理 | **uv** | 速度快，pyproject.toml 原生 |
| Excel 处理 | **openpyxl** | 纯 Python，零额外依赖 |

> **不引入的东西**：前端框架（React/Vue）、Node.js、复杂构建链。所有前端资源 CDN + 少量自写 JS。

## 七、关键技术约定

1. **URL 设计**：RESTful 风格，HTMX 触发的局部刷新路由统一以 `/partials/...` 区分（返回片段 HTML 而非整页）
2. **HTMX 用法**：表单提交、表格行内编辑、删除确认、模态框加载均用 HTMX。前端不持有业务状态
3. **金额精度**：统一 `decimal(14,2)` 存储，避免浮点；展示层千分位 + 货币符号
4. **时间统一**：所有 `period` 字段统一存当月最后一天的日期，便于排序和按月对齐
5. **错误处理**：表单错误用 HTMX 返回带错误提示的同一个 partial，不跳转
6. **CSRF**：单人使用 + 内网部署，先不上 CSRF；如未来公网暴露再加
7. **备份策略**：Docker 卷挂宿主机目录，宿主机 cron 定期复制 sqlite 文件即可
